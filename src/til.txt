
Et adapter le code JwtTokenProvider pour utiliser la nouvelle API.

LECON
Les versions milestone de Spring Boot nécessitent des dépendances à jour.

TIL-024 — Query Derivation échoue avec méthode complexe
============================================================
Date        : 2026-02-26
Projet      : Phoenix Exchange API
Catégorie   : Spring Data JPA

PROBLEME
No property 'filters' found for type 'Product' lors du démarrage Spring Boot.

CAUSE
La méthode findByFilters(category, brand, status, pageable) ne suit pas la convention de nommage Spring Data. Spring tente de chercher un attribut "filters" inexistant.

SOLUTION
Option 1 : Utiliser @Query avec JPQL
```java
@Query("SELECT p FROM Product p WHERE " +
       "(:category IS NULL OR p.category = :category) AND " +
       "(:brand IS NULL OR p.brand = :brand) AND " +
       "(:status IS NULL OR p.status = :status)")
Page<Product> findByFilters(@Param("category") String category,
                            @Param("brand") String brand,
                            @Param("status") ProductStatus status,
                            Pageable pageable);
```

Option 2 : Renommer selon convention
```java
Page<Product> findByCategoryAndBrandAndStatus(
    String category, String brand, ProductStatus status, Pageable pageable);
```

LECON
Les méthodes de repository doivent soit suivre la convention de nommage stricte, soit utiliser @Query.

TIL-030 — Lombok @Data ne génère pas les getters/setters
============================================================
Date        : 2026-02-26

Getters/setters absents malgré @Data sur les entités/DTOs.

SOLUTION
Ajouter dans pom.xml :
```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-compiler-plugin</artifactId>
    <configuration>

            <path>
                <groupId>org.projectlombok</groupId>
                <artifactId>lombok</artifactId>
                <version>${lombok.version}</version>
```

Et activer Annotation Processing dans IntelliJ :
Settings → Build → Compiler → Annotation Processors → Enable annotation processing

TIL-031 — Repository méthode retourne Optional mais service attend Entity
============================================================
Date        : 2026-02-26
Projet      : Phoenix Exchange API
Catégorie   : Spring Data JPA

PROBLEME
NullPointerException ou Optional.empty() non géré.

CAUSE
Les méthodes findById retournent Optional<Entity> mais le code appelle directement .get() sans vérification.

SOLUTION
Toujours gérer Optional :
```java
//Mauvais
Product product = productRepository.findById(id).get();

//Bon
Product product = productRepository.findById(id)
    .orElseThrow(() -> new ResourceNotFoundException("Product not found: " + id));
```

LECON
Optional doit toujours être déballé avec orElse, orElseThrow ou orElseGet.

SOLUTION
Mettre à jour le code :
```java

    .signWith(SignatureAlgorithm.HS512, secret);

// Nouveau (0.12.x)
SecretKey key = Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));

    .subject(username)
    .signWith(key);
```

TIL-046 — Variable finale requise dans une lambda
============================================================
Date        : 2026-03-23
Projet      : RememberThDay
Catégorie   : Android / Java

PROBLEME
Erreur de compilation : "Variable used in lambda expression should
be final or effectively final".

CAUSE
Le bloc de validation réassignait les variables hasSchedule,
scheduledTime, dateStr et timeStr selon la validité de la date.
Ces variables étaient ensuite capturées dans la lambda passée à
databaseWriteExecutor.execute(). En Java, une variable capturée par
une lambda doit être effectivement finale ; toute réassignation
postérieure l'en empêche.

SOLUTION
Introduire quatre variables finales juste avant la lambda
(finalHasSchedule, finalScheduledTime, finalDateStr, finalTimeStr)
qui capturent la valeur résultante après validation. Toutes les
références internes à la lambda utilisent ces copies.

LECON
Une lambda Java fige l'état des variables capturées. Si une valeur
doit changer avant la capture, on la copie dans une variable finale
locale au dernier moment.

TIL-047 — Permission SCHEDULE_EXACT_ALARM refusée (Android 13+)
============================================================
Date        : 2026-03-23
Projet      : RememberThDay
Catégorie   : Android / AlarmManager

PROBLEME
Sur Android 13+ (API 33+), les alarmes programmées via
setExactAndAllowWhileIdle() étaient soit ignorées silencieusement,
soit dégradées en planning imprécis (retards de plusieurs minutes),
sans aucune indication à l'utilisateur.

CAUSE
Android 13 a introduit une distinction entre alarmes approximatives
(autorisées par défaut) et alarmes exactes (permission
SCHEDULE_EXACT_ALARM refusée par défaut, requérant un consentement

propose d'ouvrir les paramètres ou de continuer avec le fallback
setAndAllowWhileIdle() (envoi garanti, précision moindre).

LECON
Chaque montée de version Android peut transformer une permission
implicite en permission explicite. Toujours prévoir un fallback
gracieux et informer l'utilisateur.

TIL-048 — BroadcastReceiver requiert RECEIVER_EXPORTED (Android 13+)
============================================================
Date        : 2026-03-24
Projet      : RememberThDay
Catégorie   : Android / Broadcast

PROBLEME
Crash au registerReceiver() sur Android 13+ : un receiver enregistré
dynamiquement doit déclarer explicitement s'il est exporté ou non.

CAUSE
À partir d'Android 13 (API 33+), tout receiver enregistré à
l'exécution et écoutant des broadcasts non-système doit préciser
le flag RECEIVER_EXPORTED ou RECEIVER_NOT_EXPORTED, sous peine de
SecurityException.

SOLUTION

```java
ContextCompat.registerReceiver(context, smsReceiver, filter,
```

LECON
La sécurité des composants Android se durcit à chaque version :
expliciter la portée des receivers est devenu obligatoire.

TIL-049 — SMS long tronqué (limite 160 caractères)
============================================================
Date        : 2026-03-24
Projet      : RememberThDay
Catégorie   : Android / SmsManager

PROBLEME
Les messages d'anniversaire dépassant 160 caractères étaient
tronqués ou non envoyés.

CAUSE
sendTextMessage() est limité à un seul SMS (160 caractères GSM-7).
Au-delà, le message doit être découpé en plusieurs parties.

SOLUTION
Découper le message avec divideMessage() et l'envoyer via
sendMultipartTextMessage(), de manière asynchrone :
```java
ArrayList<String> parts = smsManager.divideMessage(message);

```

LECON
Un SMS n'est pas un canal "illimité" : au-delà d'une certaine
longueur, il faut explicitement gérer le multipart.

TIL-052 — Accès index signature TypeScript (TS4111)
============================================================
Date        : 2026-05-23
Projet      : Phoenix Exchange (phoenix-ui)
Catégorie   : Angular / TypeScript strict

PROBLEME
Erreur TS4111 : "Property 'score' comes from an index signature, so
it must be accessed with ['score']" sur g.controls.score.value.

CAUSE
En mode strict, une propriété provenant d'une index signature (ici
les controls d'un FormGroup) ne peut pas être accédée en notation
pointée ; TypeScript impose la notation crochet pour signaler que la
clé n'est pas garantie statiquement.

SOLUTION
```typescript
// Avant
const scores = this.itemGroups.map(g => g.controls.score.value);
// Après
const scores = this.itemGroups.map(g => g.controls['score'].value);
```

LECON
Le mode strict distingue les propriétés déclarées des clés
dynamiques. La notation crochet documente l'accès à une clé
non typée statiquement.
